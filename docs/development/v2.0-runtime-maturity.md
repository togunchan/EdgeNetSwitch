# EdgeNetSwitch v2.0 — Runtime Maturity Development Notes

## v2.0 Objective

I started the v2.0 work with a code audit of the existing runtime and its shutdown behavior. The goal was to mature worker lifetime management, shutdown, control-plane access, and behavior under failure before adding new packet-path features.

Development began by reproducing lifecycle bugs, then securing the contracts with minimal production fixes. Telemetry and control-plane boundaries, lifecycle accounting, operational visibility, and final recovery validation followed. I used Codex for code audits and regression test preparation, keeping the fixes focused on the synchronization and ownership problems exposed by the tests.

This document records the problems, design decisions, and validation results in development order. Release preparation is separate work.

## Edgev2-001 — Runtime Lifecycle and Shutdown Safety

### Initial lifecycle audit

The initial audit exposed three concrete problems:

- Destroying a running `TelemetryExportManager` without an explicit `stop()` call terminated the child process with `SIGABRT`.
- Samples accepted after telemetry `stop()` completed remained stranded in the queue; a second `stop()` could not process them.
- Destroying `PacketStats` before the packet worker drained allowed a terminal event to reach a stale observer callback, causing `SIGSEGV`.

Lifecycle tests reproduced these behaviors before production code was changed. Crash and hang scenarios ran in child processes created with `fork()`, allowing the Catch2 parent process to observe the result. Gates controlled worker progress; the alarm served only as a final timeout for hangs.

### TelemetryExportManager lifetime

The `TelemetryExportManager` destructor had been left defaulted. Destroying a `std::thread` object while it is still `joinable()` calls `std::terminate()`. Making the destructor call `stop()` ensured that the worker finished and was joined before the manager was destroyed.

Worker execution and sample admission were treated as separate states:

- `running_` determines whether the worker exits after draining.
- `accepting_` determines whether a new sample can enter the queue.

`start()` opens admission; `stop()` closes it, drains accepted samples, and joins the worker. `enqueue()` accepts data only while admission is open. This prevents samples from accumulating after stop with no worker left to process them.

The old queue tests enqueued data before `start()`. They were updated to follow the new contract, starting the worker first and using gates to prevent assertions from racing with drain.

### PacketProcessor lifetime

The daemon constructed the objects in this order:

```cpp
PacketProcessor packetProcessor(bus, &forwardingEngine, &transportManager, failureInjector);
PacketStats packetStats(bus);
```

Stack objects are destroyed in reverse order, so `PacketStats` could die before `PacketProcessor` and its worker. The worker's final `PacketProcessed` publication then reached an observer registered with `[this]` in MessagingBus whose object no longer existed.

An explicit `PacketProcessor::stop()` was added rather than relying only on declaration order. The destructor delegated its existing worker shutdown and join logic to that function. In the daemon shutdown path, the processor was explicitly stopped after ingress shutdown, followed by the telemetry exporter. This kept `PacketStats` alive while the packet worker drained.

The lifecycle test was also updated to verify the corrected contract: while a gate holds the worker, a second packet enters the queue; after producer publications complete, the gate opens and `stop()` is called. The test verifies that both terminal events reach the observer and the queue becomes empty. The destructor remains a safe fallback after explicit stop.

### Condition-variable shutdown synchronization

The telemetry and packet workers waited while their queues were empty and the runtime was running. In the initial `stop()` implementations, however, `running_` changed outside the `queue_mutex_` used by the worker.

This separation could cause a lost wakeup: if stop changed the state and sent a notification after the worker evaluated its predicate as false but before it entered the wait, the notification would not be retained. The worker could then wait with no further notification, leaving `stop()` blocked in `join()`. Making the state atomic does not fix this protocol error by itself.

The correction uses the same invariant for both workers: shutdown state that affects the wait decision changes under the queue mutex used to evaluate the predicate, and notification occurs after releasing the lock. The worker continues processing accepted work and exits only when stop has been requested and the queue is empty.

The essential sequence in PacketProcessor is:

```cpp
{
    std::lock_guard<std::mutex> lock(queue_mutex_);
    running_.store(false, std::memory_order_relaxed);
}
cv_.notify_all();
```

On the telemetry side, the `accepting_ = false` transition also moved into the same critical section. `enqueue()` and `stop()` are ordered through the same mutex: if enqueue acquires it first, the sample is accepted and drained; if stop acquires it first, the sample is rejected.

The predicate uses the names `work_available` and `stop_requested` for readability. The synchronization fix was recorded separately as `fix(runtime): prevent lost wakeups during worker shutdown` (`2f6dc04`).

### Admission closure

PacketProcessor did not need a separate `accepting_` state; `running_` could also govern queue admission. A check at the beginning of the callback, however, does not by itself order enqueue against shutdown. Stop can run after the callback passes the check, allowing the callback to enqueue a packet afterward.

The final admission check was therefore placed in the same `queue_mutex_` critical section as queue insertion:

```cpp
std::lock_guard<std::mutex> lock(queue_mutex_);
if (!running_.load(std::memory_order_relaxed))
    return;
// Capacity checking and queue insertion occur under the same lock.
```

If enqueue acquires the lock first, the packet is accepted and drained during shutdown. If stop acquires it first, enqueue is rejected. This boundary protected the queue; the callback's pre-queue FailureInjector path was corrected separately during the final graceful-degradation audit.

### Validation

[`tests/packet_runtime_lifecycle_tests.cpp`](../../tests/packet_runtime_lifecycle_tests.cpp) and [`tests/telemetry_lifecycle_tests.cpp`](../../tests/telemetry_lifecycle_tests.cpp) covered drain/join while observers remain alive, destructor cleanup, repeated stop, and post-stop admission. The packet regression checks more than the absence of terminal events: it also calls the stopped processor's public `processLoop()` to detect any hidden, stranded packet in the queue.

Idle-worker stop tests bound shutdown completion with a timeout. Passing them does not mean they deterministically force the lost-wakeup interleaving between predicate evaluation and wait; the shared mutex protocol is the basis for that fix.

## Edgev2-002 — Telemetry Runtime Maturity

### Existing telemetry contract

After the lifecycle fixes, telemetry's existing contract under load and exporter failure was reviewed: a bounded queue, drop-oldest behavior, `dropped_count`, background export, multiple exporters, and shutdown drain. The goal was to validate existing behavior and fill gaps in coverage.

### Exporter exception isolation

`exportSample()` already called each exporter inside a separate `try/catch`. After catching one exporter's exception, it continued to the remaining exporters; catch paths existed for both `std::exception` and other exception types.

The existing test was skipped because the manager's `exportSample()` function was `noexcept`. Since exceptions were already caught inside that function, the `SKIP` rationale was invalid. The skip was removed, and the throwing exporter's call count was added to the assertions. Delivery to healthy exporters registered before and after it made exception isolation directly observable.

### Asynchronous worker recovery

The direct `exportSample()` test did not prove that the background worker continued after an exception. An async regression was added to verify that a healthy exporter registered after the throwing exporter received the first sample and that a later enqueued sample was also processed.

No production change was needed. During final validation, this coverage was strengthened to verify shutdown drain of samples queued after an exception.

### Bounded queue and drop-oldest validation

Queue tests hold the first sample at an exporter gate so that worker consumption cannot race with measurements. They verify enqueue up to capacity, enforcement of the capacity limit, removal of the oldest waiting sample, and `dropped_count` increments alongside the actual delivery order.

For example, with capacity two, enqueueing `1, 2, 3` while sample `0` is being processed leaves `2, 3` in the waiting queue. After the gate opens, the exporter sees `0, 2, 3`. Drop-oldest removes the oldest waiting sample, not the sample in flight. Admission rejection before start or after stop is not counted as a capacity drop.

### Shutdown drain

Stop closes admission while samples already accepted and retained after any drop-oldest eviction continue to be processed. The worker exits only when the queue is empty, and `stop()` does not return before join completes. Tests release the gate and call stop, then verify the empty queue and the expected sample delivery order.

### Validation

[`tests/telemetry_export_manager_tests.cpp`](../../tests/telemetry_export_manager_tests.cpp) covered exception isolation, multiple exporters, and the bounded queue contract; the telemetry lifecycle tests covered async recovery and shutdown behavior. This phase completed missing validation without adding a new exporter or retry architecture.

## Edgev2-003 — Safe Control-Plane Runtime Boundaries

The control-plane audit identified four risks: concurrent MAC table reads and writes, unsynchronized transport counter snapshots, open control admission during shutdown, and loss of an epoll stop-before-run request. No additional handler lifetime use-after-free was found in the normal shutdown sequence.

### MacTable synchronization

The packet worker could modify the `entries_` map through `learn()` and `ageOut()` while the control plane called `snapshot()`. To synchronize access to the same container, `learn()`, `lookup()`, `ageOut()`, `snapshot()`, and `size()` were protected by a shared mutex.

The mutex was made `mutable` so const readers could synchronize access without changing the data. `snapshot()` creates an independent copy under the lock, then releases it; control-plane formatting does not hold the live table. Since `size()` now acquires a mutex, its `noexcept` qualifier was removed.

### Transport counter synchronization

The control plane read `counters_`, which the packet worker updated, through a reference to the live object. `counters()` was changed to return an independent value copy. Snapshot creation, reset, and counter updates were protected by `counters_mutex_`.

The backend `transmit()` call remained outside the counter mutex. Only recording its result in the counters was locked, so network I/O would not block snapshot readers for the duration of the send.

### Control admission during shutdown

A previously received readiness event could still accept a client or dispatch a command such as `send-packet`, creating new runtime work after shutdown began. Admission state was placed in `ControlServer`, which owns command dispatch.

`closeAdmission()` closes the atomic `accepting_` flag. `processReadableEvent()` checks it before accepting a new client, and `handleClient()` checks it before dispatch. A command that has passed the final admission check may complete; closing admission is not a barrier that cancels an executing command. The daemon joins the epoll thread before proceeding with teardown, ensuring control work has finished.

The control socket is destroyed after admission closes and the epoll thread is joined. This order closes new admission while keeping handler dependencies alive until their use ends.

### Epoll stop-before-run lifecycle

Previously, `running_ = true` at the start of `run()` could overwrite an earlier `stop()` request. The main thread could then block while joining the event-loop thread.

A one-way `stop_requested_` state replaced `running_`. `run()` does not reset it; `stop()` sets it with `exchange(true)` and notifies the shutdown eventfd only on the first call. This preserves stop-before-run and avoids redundant wakeups on repeated stop. No restart contract was added for the same event-loop object.

### Validation

`MacTableTests`, `SwitchForwardingEngineTests`, and `ControlTests` were run alongside the changes. The control regression verifies, without sleeps, that `send-packet:broadcast` produces `PacketRx` while admission is open and produces no new packet after `closeAdmission()`.

[`tests/epoll_manager_tests.cpp`](../../tests/epoll_manager_tests.cpp) covers stop before run with an event already ready, including repeated stop. These tests verify the stop-before-run contract; they do not guarantee immediate cancellation of a running handler.

## Lifecycle Identity and Accounting

### Shared LifecycleIdGenerator

Fixed identities on control-plane synthetic packets could cause lifecycle collisions. `Packet::id` and `lifecycle_id` needed distinct semantics: the former may identify a synthetic/demo packet; the latter identifies a unique runtime lifecycle.

A single daemon-owned `LifecycleIdGenerator` was shared by ingress and control-plane synthetic packet paths. Two broadcast packets can therefore retain `id = 999` while receiving different lifecycle IDs. The `send-packet:broadcast` response also returns the actual lifecycle ID generated for the packet.

The control regression verified that two calls to the same command retain the fixed packet ID, receive distinct lifecycle IDs, and return responses matching those IDs.

### Active lifecycle accounting

The old pending calculation subtracted counters for different event populations:

```text
pending_terminal_events = ingress_packets - terminal_events
```

`ingress_packets` increased only on `PacketRx`, whereas the terminal count also included UDP drops before `PacketRx`. A terminal-only drop could cancel the difference while another packet was still processing. A reason such as `ValidationError` can occur both before and after ingress, so classification by reason alone was insufficient.

`active_lifecycles_` was added to track open lifecycles by identity:

- `PacketRx` adds the lifecycle to the active set unless it has already completed.
- The first `PacketProcessed` or `PacketDropped` records completion and removes the lifecycle from the active set.
- A terminal-only drop before ingress does not affect another active lifecycle.
- A repeated terminal event for the same lifecycle increments only `duplicate_events`, leaving terminal and outcome counters unchanged.

`pending_terminal_events` is now `active_lifecycles_.size()`.

MessagingBus callbacks run synchronously; an earlier subscriber may publish a terminal event before `PacketStats` receives the original `PacketRx` callback. Queue overflow is one example. The completed check preserves this terminal-before-PacketRx ordering: late `PacketRx` is observed as ingress, but the completed lifecycle is not reactivated.

### Snapshot consistency

`snapshotAt()` copies ingress, processed, terminal, duplicate, pending, and drop counters within the same `lifecycle_mutex_` critical section. This prevents those fields from being read across different points in a lifecycle transition.

This consistency does not constitute a single transaction across the entire runtime. Other measurements, such as latency, forwarding, and queue state, use their own read paths. `RuntimeStatusBuilder` composes the data, and `SnapshotPublisher` provides control readers with a snapshot that does not change after publication; readers do not hold references to live runtime containers.

### Completed lifecycle range compression

The old `completed_lifecycles_` set used for duplicate terminal detection retained one entry indefinitely for every completed lifecycle. In a long-running daemon, this per-packet retention grew with traffic.

It was replaced with an ordered representation of disjoint ranges that merges adjacent intervals:

```cpp
std::map<std::uint64_t, std::uint64_t> completed_lifecycle_ranges_;
```

Each entry represents an inclusive `[start, end]` range. For example, completing lifecycle `6` when `[1,5]` and `[7,10]` exist produces a single `[1,10]` range. `isLifecycleCompletedLocked()` checks membership; `recordCompletedLifecycleLocked()` creates ranges, extends them in either direction, bridges them, and detects duplicates.

This compresses completed history under normal monotonic generation and completion, eliminating the need for a permanent entry per packet. The representation is not strictly bounded for every possible input: arbitrary, indefinitely sparse lifecycle IDs can create an increasing number of disjoint ranges. The design relies on the normal monotonic generator and completion model.

### Validation and limitations

Packet pipeline regressions covered terminal-only drops while another lifecycle is active, duplicate terminals, terminal-before-PacketRx ordering, and late ingress within a completed range. Range tests verified duplicate accounting after bridging with `1, 3, 2`, extending forward with `10, 11`, and extending backward with `21, 20`.

`PacketPipelineTests`, `PacketRuntimeLifecycleTests`, `ReplayEquivalenceTests`, and `ReplayOutcomeEquivalenceTests` passed in the Linux dev container. This coverage verifies normal range merging and the accounting contract; it does not establish a fixed memory bound for arbitrary sparse IDs.

## Operational Visibility

### OV-1 — Packet Visibility

The first task was to correct loss of drop categories during serialization. `SimulatedLoss`, `ProcessingError`, and `InternalError` all mapped to `unknown`, allowing categories to overwrite one another in JSON. The mapping was separated as follows, while the actual `PacketDropReason::Unknown` remained `unknown`:

| PacketDropReason | Control key |
| --- | --- |
| `SimulatedLoss` | `simulated_loss` |
| `ProcessingError` | `processing_error` |
| `InternalError` | `internal_error` |
| `Unknown` | `unknown` |

Three processor queue measurements followed: `queue_depth` for waiting packets, `queue_capacity` for maximum capacity, and `queue_high_water_mark` for the largest observed waiting queue during the runtime. Depth excludes the packet currently being processed; the high-water mark does not decrease during drain.

With the worker held at a gate, tests filled the queue and verified depth, capacity, overflow, and high-water behavior. After drain, depth returned to zero while the high-water mark was retained. `RuntimeStatusBuilder` carries these values into the snapshot through `PacketMetrics`; `packet-stats` and `packet-stats:json` expose the actual numeric values.

Forwarding visibility reused the existing `ForwardingDecisionMade` event published by PacketProcessor. `PacketStats` subscribed to it without introducing a new event or subsystem:

| ForwardingAction | Lifetime counter |
| --- | --- |
| `Drop` | `forwarding_drop_decisions` |
| `Flood` | `forwarding_flood_decisions` |
| `ForwardToPorts` | `forwarding_forward_decisions` |

These are independent atomic counters. The semantic distinction remains: `ForwardingAction::Drop != PacketDropped`. A switching Drop decision is not a packet lifecycle failure; the packet may still complete with `PacketProcessed`. Forwarding counters therefore remain separate from `drops_by_reason`. Tests verified that a forwarding event alone does not change processed, terminal, or drop accounting.

Drop reason, queue, and forwarding measurements were validated through snapshot and text/JSON control tests.

### OV-2 — Egress and Health Correctness

Some backend `TransmitResult` values left `port_id` at its default of `0`. A failure on port 7 could therefore be logged against the wrong port.

Since `TransportManager` owns the requested switch port, result attribution was normalized there:

```cpp
auto result = it->second->transmit(packet);
result.port_id = port_id;
```

Tests verified preservation of the caller's requested egress port for success and for `SendFailed`, `PortDown`, `InvalidPacket`, and `BackendUnavailable`. A default or incorrect backend port no longer changes attribution.

These results are transport outcomes. Under the current PacketProcessor contract, transmit failure does not automatically produce `PacketDropped`; the packet may complete with `PacketProcessed`. Transport counters describe egress attempt outcomes, while lifecycle counters describe terminal processing outcomes.

In HealthMonitor, `HealthStatus::silence_duration_ms` existed but was not populated. Both transition events and `currentStatus()` were corrected to report elapsed time since the last heartbeat consistently with the alive/timeout evaluation.

The daemon loop order also changed. The previous `telemetry.onTick(); healthMonitor.onTick();` sequence could mask a real timeout because the synchronous telemetry event refreshed the heartbeat first. For example, a runtime stalled for 900 ms with a 500 ms timeout could appear healthy if its heartbeat was refreshed immediately before evaluation. The final order is:

```cpp
healthMonitor.onTick();
telemetry.onTick();
```

Existing silence is evaluated before the next telemetry heartbeat is produced. Health tests covered silence duration, alive/timeout consistency, timeout transitions, heartbeat recovery, and publication only on state transitions.

HealthMonitor continues to use `system_clock` directly. Timeout tests retain the existing 100 ms timeout / 150 ms sleep margin; no clock abstraction or production hook was added solely for deterministic clock-boundary testing.

### OV-3 — Operational Health

`RuntimeState` and operational health were kept as separate concepts:

| Model | Values | Question |
| --- | --- | --- |
| `RuntimeState` | `Booting`, `Running`, `Stopping` | Which lifecycle phase is the runtime in? |
| `OperationalHealth` | `Healthy`, `Degraded`, `Overloaded`, `ShuttingDown` | What are its current operating conditions? |

For example, a `Running` runtime may be `Healthy` or `Overloaded`. Health derivation was placed in `RuntimeStatusBuilder`, which already composes telemetry, heartbeat, packet statistics, and queue state; no new health subsystem was added.

The priority contract is:

```text
ShuttingDown > Overloaded > Degraded > Healthy
```

The builder first checks for `RuntimeState::Stopping`. Otherwise, a new queue overflow or current queue saturation produces Overloaded; without those signals, a dead heartbeat produces Degraded, and the remaining case is Healthy.

Lifetime `QueueOverflow > 0` was deliberately avoided as an overload condition. That approach would leave health permanently Overloaded after a single overflow. Instead, the builder remembers the last observed overflow count and uses two current signals:

- An increase in `QueueOverflow` since the previous snapshot build.
- Current `queue_depth >= queue_capacity` when `queue_capacity > 0`.

This preserves visibility of admission failure during the snapshot interval, while allowing overload to clear on the next snapshot if no new overflow occurs and the queue is no longer saturated. If the heartbeat is still dead, the result is Degraded rather than Healthy. Overload is intentionally non-sticky.

Regressions covered healthy derivation, recovery after a new overflow, continued overload during saturation, recovery after drain, and the priority order. Queue tests use gates; heartbeat degradation testing relies on the existing clock and timeout margin.

The `status` text/JSON output and command metadata were extended with `operational_health`. The same work corrected missing newlines that caused the packet-stats text fields `rx_bytes_per_sec_raw`, `terminal_events`, `duplicate_events`, and `pending_terminal_events` to run together.

For shutdown visibility, the previously late Stopping snapshot was moved to the beginning of teardown. The final daemon sequence is:

```text
shutdown request
  -> RuntimeState::Stopping
  -> build and publish STOPPING / SHUTTING_DOWN snapshot
  -> close control admission
  -> epoll stop and thread join
  -> destroy control socket
  -> ingress shutdown
  -> PacketProcessor stop: drain and join
  -> TelemetryExportManager stop: drain and join
  -> SystemShutdown event
```

Shutdown state is therefore published before control admission closes. Snapshot derivation and control serialization were validated by tests; there is no daemon integration test proving that a live control client can read the snapshot during this short window.

## Graceful Degradation and Recovery

### Graceful degradation audit

After Operational Visibility was completed, existing failure scenarios were audited as `COVERED / PARTIAL / GAP`. The review distinguished exercising a failure path from proving that subsequent work still completes after the failure.

The initial audit found one production correctness gap: the PacketProcessor callback could publish a terminal FailureInjector outcome before reaching its stopped-state admission check. Even with queue admission closed, a new post-stop `PacketRx` could produce `PacketDropped` before reaching the queue. The remaining gaps concerned completing test coverage for existing recovery contracts.

### PacketProcessor post-stop correction

The final contract is that, once `PacketProcessor::stop()` has returned, a newly published `PacketRx` must not start processor work or execute FailureInjector.

An early guard was placed before failure injection:

```cpp
const Packet *packet = std::get_if<Packet>(&msg.payload);
if (!packet || !running_.load(std::memory_order_relaxed))
    return;
```

The existing queue-locked check remains. The early guard prevents pre-queue work for a callback newly entering a stopped processor; the locked check preserves enqueue/shutdown ordering. They protect different boundaries.

The regression publishes a packet after stop for `MalformedPacket`, `ValidationError`, `SimulatedLoss`, and `ProcessingRejection`. It verifies repeated stop, an empty queue, unchanged processor terminal/drop counters, and no new `PacketProcessed` or `PacketDropped` events. `PacketStats` can still observe `PacketRx` on the bus; processor admission rejection does not prevent other subscribers from seeing the publication.

This correction was recorded in `fix(packet): reject injected failures after stop` (`134d90e`).

`stop()` is not a completion barrier for arbitrary concurrent MessagingBus callbacks that already passed the admission guard. Those callbacks may still be in the pre-queue path. Runtime teardown therefore requires packet producers, including ingress and control paths, to be quiesced before PacketProcessor shutdown.

### Telemetry exporter recovery

The final async regression uses a gate to acknowledge that a healthy exporter runs after another exporter throws on the first sample. While the worker is held on that sample, two more samples enter the queue. The gate is then released and `stop()` is called; the test does not wait for later samples to arrive before stop, leaving shutdown responsible for draining them.

The test verifies that the throwing exporter is called three times, the healthy exporter receives `101, 102, 103` in order, no samples are dropped, and the queue empties. Repeated stop is safe; the post-stop sample `999` is rejected and exporter results remain unchanged.

This validates exception isolation, continued worker execution, delivery of later queued telemetry, and shutdown drain together. No production change was required; the test was strengthened in `test(telemetry): verify drain after exporter failure` (`d9afe0d`).

### FailureInjector recovery

The packet pipeline gained a sequential failure/recovery regression using the same processor and unchanged injector:

| Injected failure | Expected PacketDropReason |
| --- | --- |
| `MalformedPacket` | `ParseError` |
| `ValidationError` | `ValidationError` |
| `ProcessingRejection` | `ProcessingError` |

A terminal failure is configured for the first lifecycle; after observing it, the test publishes a second, valid packet. A gate verifies that the live worker reaches `PacketProcessed` for that packet. After stop, the result is one drop, one processed packet, two terminals, zero duplicates, zero pending lifecycles, and an empty queue.

`SimulatedLoss` already had mixed-outcome coverage with both successful and dropped packets. This work did not add a recovery or retry mechanism to FailureInjector.

### Transport recovery

The integration-level PacketProcessor regression covers `BackendUnavailable`, `PortDown`, `InvalidPacket`, and `SendFailed` separately. The first packet goes to a backend returning the expected failure status; `tx_failed` and any applicable category counter are verified. Under the existing contract, this packet completes with `PacketProcessed` and does not produce `PacketDropped`.

After the first lifecycle completes, a second packet is routed through a healthy backend and its successful transmission is verified. Both packets' identities and payloads, forwarding events, and egress ports are checked. The final state has two processed/terminal lifecycles, zero duplicates, zero pending lifecycles, and an empty processor queue.

These tests use fake backend return statuses; they do not reproduce an operating-system transport failure or recovery of the same failed backend. They prove that a transmit failure does not prevent the processor from completing a subsequent healthy transmission.

FailureInjector and transport recovery coverage were recorded in `test(runtime): verify recovery after packet failures` (`afc2d0a`).

## Final v2.0 Validation

Final validation used the full CTest suite, including lifecycle, telemetry, control admission, epoll, accounting, snapshot/health, and recovery regressions. The initial lifecycle work established regressions that exposed each bug and then validated the contract with minimal fixes; final validation completed that approach by checking continued progress after existing failure paths.

### Sanitized Debug build

The sanitized Debug build completed successfully on Linux with GNU 13.3.0. The existing CMake option `EDGENETSWITCH_ENABLE_SANITIZERS=ON` enables AddressSanitizer and UndefinedBehaviorSanitizer together:

```text
-fsanitize=address,undefined
-fno-omit-frame-pointer
-g
```

The link step also uses `-fsanitize=address,undefined`. Final results:

| Validation | Result |
| --- | --- |
| Sanitized Debug build, GNU 13.3.0 | Successful |
| First full sanitized CTest run | 22/22 passed |
| Second full sanitized CTest run | 22/22 passed |
| Sanitizer-reported failures during these runs | None |
| `git diff --check` | Passed |

The second full run explicitly enabled leak detection and UBSan stack traces:

```text
ASAN_OPTIONS=detect_leaks=1
UBSAN_OPTIONS=print_stacktrace=1
```

These results validate the executed suite under ASan/UBSan; they do not prove correctness for every possible concurrency interleaving.

### Known limitations

- HealthMonitor tests still rely on `system_clock` and timeout margins.
- No end-to-end daemon integration test proves that a live control client can read the short `SHUTTING_DOWN` snapshot window.
- Transport recovery tests use fake backend statuses; real OS/backend failure recovery remains for later Linux/QEMU validation.
- Lifecycle range compression relies on the normal monotonic generator/completion model; indefinitely sparse IDs can increase the number of ranges.
- PacketProcessor teardown assumes producers are quiesced first, with no callbacks remaining that have already passed the admission guard.

## v2.0 Completion State

The v2.0 development scope for runtime lifecycle, telemetry, control-plane boundaries, lifecycle accounting, and operational visibility is complete. The post-stop FailureInjector gap found by the final audit was corrected, and regressions were added for continued progress after exporter, injected packet, and transport failures. Final validation results and remaining limitations are recorded above.

The design stayed within existing components: explicit shutdown managed observer lifetime, snapshots were published as copies, existing MessagingBus events were reused, and OperationalHealth was derived in the existing builder. No clock abstraction solely for testing, new health subsystem, or retry framework was added. Remaining platform and integration boundaries are documented above; the release document will be prepared separately from this development record.

## Next Milestone — ARM64 / QEMU

The v2.5 development path after v2.0 covers ARM64 cross-compilation, a QEMU ARM64 target, systemd service integration, and boot-time daemon validation. Networking, health, and telemetry behavior will be tested together on that Linux target, including real backend failure/recovery checks.

The later v3.0 goal is a `meta-edgenetswitch` Yocto layer, BitBake recipes, a minimal root filesystem, and daemon auto-start for an end-to-end embedded Linux product simulation.

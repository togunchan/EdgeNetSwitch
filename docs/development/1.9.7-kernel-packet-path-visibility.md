# EdgeNetSwitch v1.9.7 — Kernel Packet Path Visibility

## Milestone Objective and Evidence Boundary

v1.9.7 focuses on information that becomes visible between the Linux UDP
receive path and the EdgeNetSwitch packet pipeline.

The work recorded in these notes includes:

- migrating the receive call from `recvfrom()` to `recvmsg()`;
- inspecting receive message flags;
- receiving ancillary/control messages;
- reading a kernel receive timestamp;
- observing UDP socket receive-queue overflow metadata;
- exposing the receive-buffer value returned by `SO_RCVBUF`;
- measuring a kernel-to-userspace receive interval;
- distinguishing `MSG_TRUNC`, `MSG_CTRUNC`, and application validation;
- investigating MTU 1500, IPv4 fragmentation, and UDP delivery after
  reassembly;
- experimenting with receive pressure through burst traffic, the existing
  per-dispatch receive budget, and a second ingress endpoint.

This document is a record of the implementation steps and experiments I
actually performed. When I say that a behavior was validated, I mean that the
corresponding code path, log, control response, or packet capture was observed
in the experiment described here.

## Terminology and Layer Model

I use a small set of terms to keep the experiment boundaries clear:

- **IPv4 fragment:** one fragment displayed by `tcpdump` while an oversized IP
  datagram crossed the MTU-1500 veth path.
- **UDP payload:** the bytes returned to EdgeNetSwitch by `recvmsg()`.
- **EdgeNetSwitch wire-format message:** the text carried inside the UDP
  payload, including `id`, `src`, `dst`, and `payload` fields.
- **`Packet`:** the userspace object produced by parsing the wire-format
  message.
- **Socket receive queue:** the kernel-managed queue associated with a UDP
  socket. `SO_RXQ_OVFL` and `SO_RCVBUF` are handled at this socket boundary.
- **Userspace receive buffer:** the storage supplied through `iovec` to
  `recvmsg()`.
- **Application payload limit:** `MAX_PAYLOAD_SIZE = 512`, applied by the
  EdgeNetSwitch validation layer after the UDP payload has been received and
  parsed.

These terms prevent three different results from being treated as the same
problem: IPv4 fragmentation, UDP receive truncation, and application-level
`payload_too_large` rejection.

## 1. Ingress Receiver Preparation

### Receive-status naming

I first noticed a naming problem in `UdpReceiver::handleReadable()`. The
function returned this enum:

```cpp
enum class UdpReadResult
{
    PacketProcessed,
    NoData,
    Closed,
    Error
};
```

`PacketProcessed` did not describe what the function had actually completed.
The same value was returned when parsing failed, when validation rejected the
message, and when `PacketRx` was published. In the first two cases the packet
never reached `PacketProcessor`; in the last case processing had not started
yet.

I therefore changed the result model to describe the socket receive operation:

```cpp
enum class UdpReceiveStatus
{
    DatagramReceived,
    NoDataAvailable,
    Interrupted,
    Closed,
    Error
};
```

This change did not alter runtime behavior. It made the return value match the
responsibility of the function.

### The `handleReadable()` responsibility boundary

While inspecting the function, I also noticed that it already performed
several responsibilities:

- receiving UDP data;
- recording receive time;
- parsing the wire-format message;
- filling runtime fields;
- validating the parsed packet;
- publishing `PacketRx`.

The v1.9.7 roadmap would add `recvmsg()`, kernel timestamps,
`SO_RXQ_OVFL`, ancillary data, and truncation detection at the same boundary.
That meant `handleReadable()` would continue to grow and would contain both
Linux socket handling and runtime packet logic.

At this point I did not split the function. I recorded the concern and planned
to investigate smaller receive-path responsibilities in a later step.

### Why I migrated to `recvmsg()`

The original call used `recvfrom()` and returned the payload bytes, received
length, source address, source port, and `errno` on failure.

I initially described `recvfrom()` as unable to detect an oversized datagram.
That wording was too broad for Linux: datagram receive operations can also use
`MSG_TRUNC` semantics to learn the original datagram length. The important
reason for the migration was that v1.9.7 needed the output `msg_flags` field and
ancillary/control data in addition to the UDP payload.

I changed the receive preparation to this form:

```cpp
std::array<char, 1024> buffer{};

iovec io{};
io.iov_base = buffer.data();
io.iov_len = buffer.size();

sockaddr_in client_addr{};

msghdr message{};
message.msg_name = &client_addr;
message.msg_namelen = sizeof(client_addr);
message.msg_iov = &io;
message.msg_iovlen = 1;

const ssize_t len =
    ::recvmsg(socket_fd_.get(), &message, 0);
```

I deliberately kept the behavior unchanged during this first migration. The
goal was to replace the receive API and prepare the data structures required by
the later experiments.

## 2. `recvmsg()`, Ancillary Data, and Message Flags

### `msghdr`, `iovec`, and output flags

`iovec` describes the userspace payload storage. `msghdr` also carries the
source address, output flags, and the control buffer used for ancillary data.

I first added a log for `message.msg_flags`. A normal message produced:

```text
[UDP] recvmsg: len=69, flags=0x0
```

No receive condition was reported for that message.

I then reduced the userspace buffer to 16 bytes and sent a wire-format message
with an approximately 300-byte application payload. `recvmsg()` returned 16
bytes and set `MSG_TRUNC`.

The first log displayed:

```text
[UDP] recvmsg: len=16, flags=0x32
```

Later I discovered a logging mistake: the value was produced by decimal
`std::to_string()` but prefixed with `0x`. The actual value was decimal 32,
which was later logged correctly as hexadecimal `0x20`.

I also added symbolic checks:

```cpp
if (message.msg_flags & MSG_TRUNC)
{
    Logger::info("[UDP] MSG_TRUNC");
}

if (message.msg_flags & MSG_CTRUNC)
{
    Logger::info("[UDP] MSG_CTRUNC");
}
```

The repeated truncation experiment produced:

```text
[UDP] MSG_TRUNC
```

The later receive-layer classification of this condition is documented in
Section 7.

### Allocating and iterating ancillary data

To receive the kernel timestamp, I added a control buffer:

```cpp
std::array<std::byte, CMSG_SPACE(sizeof(timespec))> control_buffer{};

message.msg_control = control_buffer.data();
message.msg_controllen = control_buffer.size();
```

At first I thought `sizeof(timespec)` would be sufficient. I then learned that
the control element also contains a `cmsghdr` and padding. `CMSG_SPACE()`
accounts for the header and the space required for the element.

I iterated the returned elements with the control-message macros:

```cpp
for (cmsghdr* control = CMSG_FIRSTHDR(&message);
     control != nullptr;
     control = CMSG_NXTHDR(&message, control))
{
    // Inspect the control element.
}
```

The first diagnostic observation was:

```text
[UDP] control message: level=1, type=35, len=32
```

### `MSG_CTRUNC` experiment

After timestamp and overflow metadata were both supported, the normal control
capacity was:

```cpp
constexpr std::size_t control_buffer_size =
    CMSG_SPACE(sizeof(timespec)) +
    CMSG_SPACE(sizeof(std::uint32_t));
```

To force control-data truncation, I temporarily changed only the length passed
to the kernel:

```cpp
message.msg_control = control_buffer.data();
message.msg_controllen = 1;
```

The result was:

```text
[UDP] recvmsg: len=77, flags=0x8
[UDP] MSG_CTRUNC
```

The UDP payload continued through the packet pipeline:

```text
Packet received
ForwardingDecisionMade
PacketProcessed
```

In this one-byte experiment, the expected ancillary metadata was absent:

```text
kernel_receive_realtime_ns=none
kernel_receive_drop_count=none
```

I then restored the real capacity:

```cpp
message.msg_controllen = control_buffer.size();
```

The next receive returned no message flags, and timestamp metadata was present
again:

```text
[UDP] recvmsg: len=77, flags=0x0
[UDP] No message flags
[UDP] kernel timestamp: sec=1786109400, nsec=34284304
```

## 3. Kernel Receive Timestamp

### Enabling `SO_TIMESTAMPNS`

Before this experiment I recorded only a userspace ingress time after the
receive call. I wanted to read the receive timestamp supplied by Linux for the
datagram.

I enabled `SO_TIMESTAMPNS` during socket initialization:

```cpp
int enable_timestamping = 1;

if (::setsockopt(socket_fd_.get(),
                 SOL_SOCKET,
                 SO_TIMESTAMPNS,
                 &enable_timestamping,
                 sizeof(enable_timestamping)) < 0)
{
    throw std::runtime_error(
        "Failed to enable UDP receive timestamping");
}
```

The option prepares timestamp metadata for later `recvmsg()` calls. The
application must still provide a control buffer and find the matching control
element.

### Extracting `SCM_TIMESTAMPNS`

I checked the symbolic level and type before reading the timestamp:

```cpp
if (control->cmsg_level == SOL_SOCKET &&
    control->cmsg_type == SCM_TIMESTAMPNS)
{
    const auto* kernel_timestamp =
        reinterpret_cast<const timespec*>(CMSG_DATA(control));
}
```

The first successful result was:

```text
[UDP] kernel timestamp: sec=1784982884, nsec=759359840
```

I converted the seconds and nanoseconds into one value:

```text
seconds × 1,000,000,000 + nanoseconds
```

The timestamp used `CLOCK_REALTIME` semantics. In the rest of the note I refer
to this value as the kernel receive timestamp.

### Propagating the timestamp

I added optional kernel metadata to `Packet`:

```cpp
std::optional<std::uint64_t> kernel_receive_realtime_ns;
std::optional<std::uint32_t> kernel_receive_drop_count;
```

The fields were optional because the same ancillary values were not present in
every observed receive. Timestamp metadata appeared on normal receives after
`SO_TIMESTAMPNS` was enabled, while the overflow field was absent until the
overflow experiment produced a value.

For one normal datagram I observed:

```text
[UDP] kernel timestamp: sec=1785006008, nsec=526605386
[Packet] kernel_receive_realtime_ns=1785006008526605386
```

The conversion matched:

```text
1785006008 × 1,000,000,000
+ 526605386
= 1785006008526605386
```

This verified that the timestamp value extracted by `UdpReceiver` was
preserved in the `Packet` for the tested normal receive.

I then added last-observed kernel metadata fields to `PacketStats` and exposed
them through `packet-stats`. The update occurs in the `PacketRx` subscriber.

The JSON validation returned:

```json
{
  "data": {
    "ingress_packets": 2,
    "last_kernel_receive_drop_count": 0,
    "last_kernel_receive_realtime_ns": 1785008925683082295,
    "processed_packets": 2,
    "processing_gap": 0
  },
  "status": "ok"
}
```

The corresponding timestamp log was:

```text
kernel timestamp: sec=1785008925, nsec=683082295
```

The conversion again matched the value in the control response.

## 4. UDP Socket Receive-Queue Drop Visibility

### Enabling and extracting `SO_RXQ_OVFL`

I enabled overflow reporting on the UDP socket:

```cpp
int enable_rxq_overflow = 1;

::setsockopt(socket_fd_.get(),
             SOL_SOCKET,
             SO_RXQ_OVFL,
             &enable_rxq_overflow,
             sizeof(enable_rxq_overflow));
```

I then searched the returned `SOL_SOCKET` control elements for
`SO_RXQ_OVFL` and read the `uint32_t` drop-count value.

During the first normal receive I did not find the expected element. At first I
thought the extraction was wrong. I then noticed that no receive-queue overflow
had occurred in that test; only the timestamp control element was present.

The overflow experiment described in Section 9 later produced:

```text
[UDP] kernel receive queue drops=75482
```

That observation verified that a positive overflow value could be read from
ancillary data in the tested runtime.

The later single-socket burst used for drain-budget validation produced
another visible value:

```text
[UDP] kernel receive queue drops=1781
```

### Runtime propagation

The optional drop-count field was copied into `Packet` when the control element
was present:

```cpp
packet.kernel_receive_drop_count =
    kernel_receive_drop_count;
```

`PacketStats` updated its last-observed value only when the optional field was
present. If a later `PacketRx` did not contain the overflow element, the
previous stored value was retained.

The `Packet` representation and `PacketStats` representation intentionally had
different absence behavior:

```text
Packet:      kernel_receive_drop_count=none
PacketStats: last_kernel_receive_drop_count=0
```

The snapshot used a zero-initialized scalar, so these two states were not
distinguished:

```text
No SO_RXQ_OVFL metadata has been observed.

SO_RXQ_OVFL metadata was observed with a value represented as zero.
```

I decided not to add a separate availability field at this stage. I recorded
that an optional snapshot field or explicit availability value could be added
later if a concrete use case required the distinction.

## 5. Socket Receive Buffer Observability

### Reading `SO_RCVBUF`

After the ancillary metadata work, I considered whether `SO_RCVBUF` belonged in
`Packet`. I decided that it did not: the receive-buffer setting belongs to the
socket rather than one datagram.

I first queried it during socket initialization:

```cpp
int receive_buffer_bytes = 0;
socklen_t option_length = sizeof(receive_buffer_bytes);

if (::getsockopt(socket_fd_.get(),
                 SOL_SOCKET,
                 SO_RCVBUF,
                 &receive_buffer_bytes,
                 &option_length) < 0)
{
    throw std::runtime_error(
        "Failed to read UDP receive buffer size");
}
```

The startup logs showed:

```text
[UDP] effective SO_RCVBUF=212992 bytes
[UDP] effective SO_RCVBUF=212992 bytes
```

The two lines came from the two UDP ingress sockets. `212992` was the value
returned by Linux for each socket.

### Per-endpoint `ingress-stats`

I did not want the value to remain only in startup logs. I stored the value in
`UdpReceiver` and introduced a per-socket snapshot:

```cpp
struct IngressSocketSnapshot
{
    std::uint32_t switch_port{0};
    std::uint16_t listen_port{0};
    int fd{-1};
    std::uint32_t receive_buffer_bytes{0};
};
```

`IngressManager::snapshot()` iterates the active receivers and returns one
snapshot per ingress socket. I exposed this through a new control command:

```text
ingress-stats
```

The JSON validation returned:

```json
{
  "data": {
    "ingress_sockets": [
      {
        "fd": 9,
        "listen_port": 9001,
        "receive_buffer_bytes": 212992,
        "switch_port": 1
      },
      {
        "fd": 10,
        "listen_port": 9002,
        "receive_buffer_bytes": 212992,
        "switch_port": 2
      }
    ]
  },
  "status": "ok"
}
```

The text response was also verified:

```text
ingress_socket_count=2
switch_port=1 listen_port=9001 fd=9 receive_buffer_bytes=212992
switch_port=2 listen_port=9002 fd=10 receive_buffer_bytes=212992
```

The resulting path was:

```text
Linux socket
    ↓
getsockopt(SO_RCVBUF)
    ↓
UdpReceiver
    ↓
IngressManager::snapshot()
    ↓
ControlContext
    ↓
ingress-stats
```

## 6. Kernel-to-Userspace Receive Timing

### Discovering the clock-domain mismatch

At this point `Packet` contained two timestamps:

```cpp
kernel_receive_realtime_ns
ingress_timestamp_ns
```

`kernel_receive_realtime_ns` came from `SO_TIMESTAMPNS` and used realtime
semantics. `ingress_timestamp_ns` came from `std::chrono::steady_clock` and was
monotonic. Even though both were represented in nanoseconds, subtracting them
would not produce a meaningful duration because they belonged to different
clock domains.

I kept the existing monotonic `nowNs()` helper for processing durations and
added a realtime helper:

```cpp
inline std::uint64_t nowRealtimeNs()
{
    return static_cast<std::uint64_t>(
        std::chrono::duration_cast<std::chrono::nanoseconds>(
            std::chrono::system_clock::now().time_since_epoch())
            .count());
}
```

I sampled it immediately after a successful `recvmsg()` so logging, ancillary
parsing, packet parsing, and validation would not be included before the
userspace timestamp:

```cpp
const ssize_t len = ::recvmsg(socket_fd_.get(), &message, 0);

// Error handling occurs before this point.
const auto userspace_receive_realtime_ns = nowRealtimeNs();
```

### Optional latency calculation

When the kernel timestamp was present and the userspace realtime value was not
earlier, I calculated:

```cpp
std::optional<std::uint64_t>
    kernel_to_userspace_receive_latency_ns;

if (kernel_receive_realtime_ns &&
    userspace_receive_realtime_ns >= *kernel_receive_realtime_ns)
{
    kernel_to_userspace_receive_latency_ns =
        userspace_receive_realtime_ns -
        *kernel_receive_realtime_ns;
}
```

The result remained optional. If the kernel timestamp was absent or realtime
ordering appeared reversed, I preferred `none` to an ambiguous zero.

The measurement represented this path:

```text
kernel receives datagram
        ↓
socket receive queue
        ↓
epoll wakeup / scheduling
        ↓
recvmsg() returns
        ↓
userspace realtime timestamp
```

I explicitly separated this value from network latency. It measured the
receive interval represented by the kernel timestamp and the userspace sample
immediately after `recvmsg()`.

### Observed values and control-plane propagation

The first observed sample group was:

```text
800792 ns
584500 ns
844875 ns
347959 ns
730583 ns
447917 ns
523459 ns
761667 ns
625042 ns
640542 ns
```

In that run the values were approximately 0.35–0.85 ms.

I added the optional value to `Packet`, updated the last-observed value through
`PacketStats`, and exposed it through `packet-stats`.

During the first validation I found that
`last_kernel_receive_realtime_ns` and
`last_kernel_to_userspace_receive_latency_ns` contained the same timestamp.
The calculation was correct; the designated initializer in
`PacketStats::snapshotAt()` assigned the realtime timestamp variable to the
latency field.

After correcting that error, the response contained:

```json
{
  "last_kernel_receive_realtime_ns": 1786112255693168042,
  "last_kernel_to_userspace_receive_latency_ns": 251791
}
```

`251791 ns` is approximately 252 microseconds and matched the magnitude of the
earlier runtime observations.

During the later single-socket pressure experiment in Section 9, the recorded
values increased to approximately 100 ms. The detailed samples and the burst
conditions are preserved with that experiment.

## 7. UDP Receive Truncation and Protocol Validation

### Initial behavior

The first `MSG_TRUNC` experiment temporarily reduced the userspace receive
buffer to 16 bytes and sent a larger wire-format message.

`recvmsg()` returned:

```text
[UDP] recvmsg: len=16, flags=0x20
[UDP] MSG_TRUNC
```

The parser saw only the beginning of the message:

```text
id=1;
src=00:11:
```

and reported a parse failure.

In the later receive flow, a truncated datagram could continue into parsing and
validation, producing an application-level result such as:

```text
MSG_TRUNC
...
Packet rejected: reason=payload_too_large
```

I then realized that this classification started too late. The UDP payload had
already failed to fit in the userspace receive buffer, so the primary failure
belonged to the receive layer rather than application validation.

### `DatagramTruncated` as a terminal receive result

I added:

```cpp
PacketDropReason::DatagramTruncated
```

and changed the receive path to terminate before parsing:

```text
recvmsg()
→ MSG_TRUNC
→ PacketDropped(DatagramTruncated)
→ return
```

The repeated experiment produced:

```text
[UDP] recvmsg: len=1024, flags=0x20
[UDP] MSG_TRUNC
[DROP][UDP][TRUNCATED] Datagram exceeded receive buffer capacity
```

The control-plane response included:

```json
{
  "drops": {
    "datagram_truncated": 1
  },
  "ingress_packets": 0,
  "processed_packets": 0,
  "terminal_events": 1
}
```

The datagram ended as a terminal receive-layer drop before it became a valid
`PacketRx`.

### Receive capacity versus application payload policy

The original userspace receive buffer was:

```cpp
std::array<char, 1024> buffer{};
```

For a typical MTU-1500 IPv4/UDP path, removing a 20-byte IPv4 header and an
8-byte UDP header leaves approximately 1472 bytes for UDP payload when no IPv4
options are present.

I replaced the unnamed array size with:

```cpp
static constexpr std::size_t UDP_RECEIVE_BUFFER_SIZE = 2048;
```

This is the userspace capacity for one UDP payload/wire-format message. It is
separate from the EdgeNetSwitch application policy:

```cpp
static constexpr std::size_t MAX_PAYLOAD_SIZE = 512;
```

An approximately 1200-byte application payload produced this receive result:

```text
[UDP] recvmsg: len=1261, flags=0x0
[UDP] No message flags
```

The complete message then reached validation and was rejected:

```text
Packet rejected: reason=payload_too_large
```

This experiment separated receive capacity from the application payload limit.

## 8. MTU, IPv4 Fragmentation, and Reassembly

### Creating an MTU-1500 path

The existing container interfaces used MTUs of 65535 and 65536, so the message
sizes I wanted to test did not naturally create fragmentation there.

I added `NET_ADMIN` and `SYS_ADMIN` to the devcontainer environment and created
the veth/network-namespace topology recorded earlier.

I first validated connectivity:

```text
3 packets transmitted, 3 received, 0% packet loss
```

I then sent a small EdgeNetSwitch message across the path:

```text
[UDP] recvmsg: len=69, flags=0x0
[UDP] No message flags
[UDP] Packet received
```

This verified the normal receive path before the fragmentation experiment.

### Fragmentation experiment

While capturing `veth-a` with `tcpdump`, I sent a message containing an
approximately 1800-byte application payload from the network namespace.

EdgeNetSwitch observed:

```text
[UDP] recvmsg: len=1861, flags=0x0
[UDP] No message flags
[UDP] Packet received (1861 bytes)
```

Here `1861` is the number of UDP payload bytes returned by `recvmsg()`.

The packet capture showed two IPv4 fragments:

```text
id 34335, offset 0, flags [+], length 1500
id 34335, offset 1480, flags [none], length 409
```

Both fragments had the same IPv4 identification value in the captured flow.
The first used offset 0 and indicated that more fragments followed. The second
used offset 1480 and had no More Fragments flag.

The direct observations were:

- `tcpdump` showed the two related IPv4 fragments;
- `recvmsg()` returned one 1861-byte UDP payload;
- `MSG_TRUNC` was not set.

From those observations I concluded that Linux had reassembled the IPv4
fragments before UDP delivered the payload to the socket. The capture displayed
the fragments; the complete UDP receive was the evidence used for the
reassembly conclusion.

The application then rejected the parsed payload:

```text
Packet rejected: reason=payload_too_large
```

The final distinction from the experiment was:

```text
IPv4 fragmentation
→ MTU-related IP/network behavior

MSG_TRUNC
→ complete UDP payload does not fit the userspace receive buffer

payload_too_large
→ EdgeNetSwitch application payload policy
```

## 9. Ingress Pressure, Drain Budget, and Fairness

The receive-pressure history began with the `SO_RXQ_OVFL` experiment and later
continued with validation of the existing per-dispatch receive budget and a
two-endpoint marker experiment.

### First burst sender

I temporarily reduced the socket receive buffer and sent 20,000 intended
wire-format messages through one Bash `/dev/udp` descriptor:

```bash
exec 3>/dev/udp/127.0.0.1/9001

for i in {1..20000}; do
    printf 'id=%d;\nsrc=00:11:22:33:44:55;\ndst=ff:ff:ff:ff:ff:ff;\npayload=OverflowTest\n' \
        "$i" >&3
done

exec 3>&-
```

I expected one logical EdgeNetSwitch message per UDP datagram. Instead, the
receiver observed separate pieces:

```text
data=[id=19170;]
data=[src=00:11:22:33:44:55;]
data=[dst=ff:ff:ff:ff:ff:ff;]
data=[payload=OverflowTest]
```

This showed that the sender command was producing multiple UDP datagrams for
one intended logical message.

During that run the runtime observed:

```text
[UDP] kernel receive queue drops=75482
```

This was the positive overflow observation used to validate the
`SO_RXQ_OVFL` extraction path.

### Revised sender construction

I then constructed each logical message in a variable before writing it:

```bash
exec 3>/dev/udp/127.0.0.1/9001

for i in {1..20000}; do
    printf -v packet \
        'id=%d;\nsrc=00:11:22:33:44:55;\ndst=ff:ff:ff:ff:ff:ff;\npayload=OverflowTest\n' \
        "$i"

    printf '%s' "$packet" >&3
done

exec 3>&-
```

This time the runtime parsed and processed the messages:

```text
PacketProcessed: lifecycle_id=1263 packet_id=19745
```

In this run I did not observe another receive-queue overflow while the runtime
processed approximately 20,000 intended messages. I treated this as a local
observation about that test environment and accepted the earlier positive
overflow log as validation of the `SO_RXQ_OVFL` integration.

### Existing per-dispatch receive budget

I later tried to validate how the receive drain limit already present in
`UdpReceiver::processReadableEvent()` behaved under load.

The receiver did not drain a UDP socket without a bound after an epoll
readiness event:

```cpp
constexpr std::size_t MaxPacketsPerWakeup = 256;
```

The counter increased while `handleReadable()` returned successfully received
datagrams. If 256 datagrams were processed before the socket became empty, the
loop ended and logged:

```text
[UDP] receive budget exhausted
```

I first checked how this behavior related to the epoll registration:

```cpp
epollManager_.add(endpoint.receiver->fd(), EPOLLIN);
```

`EPOLLET` was not used, so the UDP sockets were registered with level-triggered
epoll. If one receive dispatch stopped after 256 datagrams while unread
datagrams remained, the fd stayed readable and could be reported as `EPOLLIN`
again by a later `epoll_wait()` call.

### An insufficient load attempt

My first load test started a separate `nc` process for each datagram:

```bash
for i in {1..5000}; do
    printf "id=%d;\nsrc=00:11:22:33:44:55;\ndst=ff:ff:ff:ff:ff:ff;\npayload=Load\n" "$i" \
    | nc -u -q 0 127.0.0.1 9001
done
```

The logs repeatedly showed:

```text
[EPOLL] UDP readable
[UDP] drained queue packets=1
```

Each iteration created a new `nc` process and UDP socket. The runtime had time
to empty the receive socket between datagrams: one datagram was read for each
readiness event, and the next non-blocking receive found the socket empty. This
test did not trigger the 256-datagram receive budget.

### Single-socket burst and drain-budget observation

I then kept one `/dev/udp` socket open and sent 5,000 datagrams back to back:

```bash
exec 3>/dev/udp/127.0.0.1/9001

for i in {1..5000}; do
    printf -v packet \
        'id=%d;\nsrc=00:11:22:33:44:55;\ndst=ff:ff:ff:ff:ff:ff;\npayload=Load\n' \
        "$i"

    printf '%s' "$packet" >&3
done

exec 3>&-
```

This test produced receive pressure. I observed a receive-queue drop value:

```text
[UDP] kernel receive queue drops=1781
```

The received packet IDs also contained large gaps even though the sender
generated sequential IDs.

During the same experiment, the kernel-to-userspace receive interval increased
to approximately 100 ms:

```text
packet kernel-to-userspace latency=98619667 ns
packet kernel-to-userspace latency=99192459 ns
packet kernel-to-userspace latency=100716750 ns
packet kernel-to-userspace latency=104068709 ns
```

This made the increase in the recorded receive interval under receive-queue
pressure visible.

For the first time in these tests, I also observed the drain budget being
reached:

```text
[UDP] receive budget exhausted
[EPOLL] UDP readable
```

A receive dispatch ended after processing 256 datagrams and returned control
to the event loop. Because the socket was still readable, its UDP fd was
reported as `EPOLLIN` again and processing continued. This observation matched
the behavior I expected from the existing 256-datagram receive budget and the
level-triggered epoll registration.

### Bounded draining, not network traffic pacing

This mechanism did not change the sender's packet rate. I therefore described
it as bounded ingress draining, or a per-dispatch receive budget, rather than
network traffic pacing:

```text
EPOLLIN
    ↓
process at most 256 datagrams
    ↓
return control to the event loop
    ↓
if the socket is still readable, epoll reports it again
```

### Two-endpoint marker experiment

Finally, I checked whether a second ingress endpoint could be processed while
port 9001 remained under heavy load. For the load side of this experiment I
increased the same single-socket burst to 50,000 datagrams:

```bash
exec 3>/dev/udp/127.0.0.1/9001

for i in {1..50000}; do
    printf -v packet \
        'id=%d;\nsrc=00:11:22:33:44:55;\ndst=ff:ff:ff:ff:ff:ff;\npayload=LOAD\n' \
        "$i"

    printf '%s' "$packet" >&3
done

exec 3>&-
```

From another terminal I sent one marker datagram to port 9002. My first marker
command accidentally split the message into multiple UDP datagrams, and the
parser rejected the pieces separately.

I corrected the sender by building the marker in one buffer and writing it
once:

```bash
printf -v marker \
'id=999999;\nsrc=00:aa:bb:cc:dd:ee;\ndst=ff:ff:ff:ff:ff:ff;\npayload=FAIRNESS_MARKER\n'

exec 4>/dev/udp/127.0.0.1/9002
printf '%s' "$marker" >&4
exec 4>&-
```

The logs then showed:

```text
PacketProcessed: ... packet_id=8662

[EPOLL] UDP readable
[UDP] recvmsg: len=81, flags=0x0
[UDP] Packet received (81 bytes)

Packet received: id=999999 payload=FAIRNESS_MARKER
source_ip=127.0.0.1
ingress_port=2

[UDP] drained queue packets=1

PacketProcessed: ... packet_id=999999
```

The marker was received and processed through port 9002 while the load on port
9001 continued.

This experiment alone did not prove that the marker was processed immediately
after one specific `receive budget exhausted` event. Together with the earlier
drain-budget experiment, it supported the following recorded conclusions:

- the 256-datagram receive budget was triggered under burst load;
- the receiver returned control to the event loop at the budget boundary;
- the level-triggered epoll registration allowed the still-readable UDP fd to
  be reported again;
- another ingress endpoint was processed while the first endpoint was under
  load;
- receive-queue drops became visible under pressure;
- the kernel-to-userspace receive interval increased under the same pressure.

At this stage I did not observe behavior in the existing ingress drain
mechanism that required a new architectural change.

## Architectural Decisions

The following decisions were made during the recorded investigation:

1. Rename the receive result so it represents socket receive status rather than
   packet-processing completion.
2. Migrate to `recvmsg()` to obtain output flags and ancillary/control data.
3. Represent kernel timestamp and receive drop-count metadata as optional
   fields on `Packet`.
4. Store last-observed kernel metadata in `PacketStats` and expose it through
   `packet-stats`.
5. Keep `SO_RCVBUF` information at socket scope and expose one record per
   ingress socket through `ingress-stats`.
6. Keep the existing monotonic timestamp for runtime durations and introduce a
   separate realtime timestamp for comparison with `SO_TIMESTAMPNS`.
7. Classify `MSG_TRUNC` as the terminal receive-layer reason
   `DatagramTruncated`.
8. Replace the unnamed 1024-byte receive array with a named 2048-byte receive
   capacity while keeping `MAX_PAYLOAD_SIZE = 512` as a separate application
   rule.
9. Leave the snapshot distinction between an absent drop-count observation and
   zero unmodeled until a concrete need appears.

## Open Points Recorded During the Work

Two follow-up considerations were explicitly recorded in the original notes:

- `handleReadable()` combines Linux receive handling with parsing, validation,
  runtime-field population, and event publication. I deferred investigating a
  smaller responsibility split.
- `Packet` can represent an absent receive drop-count value, while the current
  snapshot scalar begins at zero. I decided not to add availability state or an
  optional snapshot field without a concrete use case.

## Architectural Conclusions

The receive path changed from reading only UDP payload bytes and a source
address to reading message flags and ancillary metadata through `recvmsg()`.

The runtime could then expose:

- the kernel receive timestamp returned through `SCM_TIMESTAMPNS`;
- the receive drop-count value observed through `SO_RXQ_OVFL`;
- the receive-buffer value returned for each ingress socket;
- the calculated kernel-to-userspace receive interval;
- an explicit terminal counter for truncated datagrams.

The experiments also separated three layers that had initially been easy to
confuse:

```text
IPv4 fragmentation
→ MTU-related IP/network behavior

MSG_TRUNC
→ userspace receive-buffer capacity

payload_too_large
→ EdgeNetSwitch application policy
```

The MTU-1500 experiment showed two IPv4 fragments in `tcpdump` and one complete
1861-byte UDP payload at `recvmsg()`. The earlier receive-pressure experiment
produced a positive overflow observation after the first Bash sender
unexpectedly split logical messages across multiple UDP datagrams.

The later single-socket burst triggered the existing 256-datagram receive
budget, made another receive-queue drop value visible, and increased the
recorded kernel-to-userspace receive interval to approximately 100 ms. After
the budget was exhausted, control returned to the event loop and the
level-triggered epoll registration reported the still-readable UDP fd again.

During the two-endpoint experiment, the marker on port 9002 was received and
processed while port 9001 remained under load. That experiment did not prove
that the marker was processed immediately after one particular
`receive budget exhausted` event. Together with the drain-budget observation,
it showed the recorded behavior of the existing bounded ingress drain without
revealing a need for a new architectural change.

Together, these steps made the Linux UDP receive path more visible inside the
runtime and made receive-layer conditions distinguishable from application
validation results.

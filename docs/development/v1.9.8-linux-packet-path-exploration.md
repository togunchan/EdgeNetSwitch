# EdgeNetSwitch v1.9.8 — Linux Packet Path Exploration

## 1. Research Goal and Starting Point

Today, EdgeNetSwitch's UDP ingress path conceptually works as follows:

```text
UdpReceiver
    ↓
AF_INET / SOCK_DGRAM
    ↓
bind(IP, UDP port)
```

For example:

```text
0.0.0.0:5000
```

In broad terms, we are telling the kernel:

> "I want the UDP datagrams delivered to port 5000."

On the AF_PACKET side, the model will look like this:

```text
AF_PACKET / SOCK_RAW
    ↓
bind(interface index)
```

For example:

```text
veth1
```

Here, in broad terms, we will be telling the kernel:

> "I want the Layer-2 packets you see on veth1."

The difference between these two approaches is important.

A UDP socket gives us the datagram delivered by the kernel after IP and UDP processing.

AF_PACKET gives us access to a lower-level packet representation.

The central question of this investigation is: At which point does userspace attach to the Linux networking stack, and how does that point change the packet structure I see? I follow the AF_PACKET, TAP/TUN, and Linux bridge experiments, followed by receive queue and RSS/RPS/RFS configuration observations, around this question.

## 2. AF_PACKET — Going Below the UDP Socket Boundary

### AF_PACKET and AF_INET: Addressing and Attachment Models

First, I want to clarify what `AF_PACKET` is.

So far, I have used the following structure in EdgeNetSwitch:

```cpp
const int raw_fd = ::socket(AF_INET, SOCK_DGRAM, 0);
```

Here, `AF_INET` specifies that the socket will operate in the IPv4 protocol family.

`SOCK_DGRAM`, in the context of `AF_INET`, leads us to the UDP datagram model.

If we used `AF_PACKET` instead of `AF_INET`, we would be telling the kernel, in broad terms:

> "I do not want an application socket at the IP/UDP level. I want access to packets at the network-device level."

The fundamental difference in perspective is:

`AF_PACKET`:

> "What kind of frame arrived on the interface?"

asks the question,

UDP socket:

> "Which UDP datagram did the kernel deliver to me?"

asks the question.

So what is `SOCK_RAW`?

When we use `SOCK_RAW` with `AF_PACKET`, the link-layer header is also delivered to userspace.

This behavior is stated explicitly in the Linux `packet(7)` documentation:

https://man7.org/linux/man-pages/man7/packet.7.html

When using Ethernet, this means that userspace can see not only the application payload, but packet data beginning with the Ethernet header.

I will also use `ETH_P_ALL` in the first experiment.

This lets us request packets for all Ethernet protocol types from the packet socket.

At first, I want to observe the traffic more generally instead of applying a specific EtherType filter.

I previously used `sockaddr_in` on the normal UDP socket side.

`sockaddr_in` essentially represents IPv4 endpoint information.

For example:

```text
127.0.0.1:5000
```

Here:

```text
127.0.0.1 -> IPv4 address
5000      -> port
```

In the AF_PACKET world, addressing occurs at the Layer-2/network-device level, so we will use `sockaddr_ll`.

The central question is now:

```text
Which IP and port?
```

rather than:

```text
Which network interface?
```


This also introduces the concept of an interface index.

As I investigate and implement this, I will also note what `sockaddr_ll`, the interface index, and the other fields do.

I also want to address an important misconception from the outset:

`AF_PACKET` is not a kernel-bypass mechanism.

Packet sockets are still part of the Linux kernel networking mechanism.

The difference is:

It gives userspace packet access at a lower point in the network stack than a normal UDP socket.

Linux also provides more advanced AF_PACKET mechanisms such as `PACKET_MMAP` for packet capture and transmission.

I will not move on to those at this stage.

First, I want to understand basic AF_PACKET behavior through a small, isolated experiment.

### Inspecting the Ethernet Header

Ethernet header structure:

```text
byte offset

0                6               12      14
|----------------|----------------|-------|
 Destination MAC    Source MAC    EtherType
     6 bytes          6 bytes       2 bytes
```

Therefore:

```text
bytes[0..5]    = Destination MAC
bytes[6..11]   = Source MAC
bytes[12..13]  = EtherType
```

To reach the EtherType field, I moved 12 bytes forward from the start of the buffer:

```cpp
std::memcpy(&ether_type, bytes + 12, sizeof(ether_type));
```

Here:

```cpp
bytes + 12
```

moves 12 bytes forward from the beginning of the frame buffer and points to the start of the EtherType field.

Because EtherType arrives in network byte order:

```cpp
ether_type = ntohs(ether_type);
```

I used this conversion.

`ntohs()`:

```text
network-to-host short
```

means network-to-host short and converts a 16-bit value from network byte order to host byte order.

In another ping attempt, the observer then produced this output:

This time, I observed `EtherType = 0x0800` directly in the Ethernet header.

## 3. AF_PACKET SOCK_RAW and SOCK_DGRAM

The code initially looked like this:


With `SOCK_RAW`, I could see the entire Layer-2 frame in userspace, including the Ethernet header.

To examine `AF_PACKET + SOCK_DGRAM` behavior, I changed the socket as follows:

```cpp
const int fd = ::socket(AF_PACKET, SOCK_DGRAM, htons(ETH_P_ALL));
```

The primary difference I expected was that the Ethernet header would not be present in the receive buffer.

Previously, when I sent a 15-byte payload with `SOCK_RAW`, I received 57 bytes in total:

Because I expected the Ethernet header to be absent from the `SOCK_DGRAM` buffer, I expected to see 14 fewer bytes for the same traffic.

The reason was that the parser was still written for `SOCK_RAW` behavior.

### 0x45: IPv4 Version and IHL

The first byte of the receive buffer being `0x45` also shows that the buffer now begins directly with the IPv4 header.

`0x45` in binary:

```text
0100 0101
^^^^ ^^^^
  |     |
  |     +---- IHL = 5
  |
  +---------- Version = 4
```

The first four bits carry the IP version:

```text
0100 = 4
```

which means IPv4.

The last four bits carry the IHL value:

```text
0101 = 5
```

`IHL` means `Internet Header Length`.

The `5` here does not mean that the header is five bytes long. Because the IHL unit is a `32-bit word`:

```text
IHL = 5
1 word = 32 bit = 4 byte
```

Therefore:

```text
5 × 4 byte = 20 byte
```

gives the IPv4 header length.

This experiment directly demonstrated the fundamental difference between `AF_PACKET + SOCK_RAW` and `AF_PACKET + SOCK_DGRAM`:

```text
SOCK_RAW
    ↓
Ethernet header included

SOCK_DGRAM
    ↓
Ethernet header absent from the receive buffer
    ↓
Buffer begins directly with the network-layer packet
```

## 4. TAP and TUN — Virtual Network Interfaces

### Difference from the AF_PACKET Attachment Model

I will now begin examining the TAP/TUN concepts.

I want to start by asking the right question:

If AF_PACKET, TAP, and TUN all carry network data to userspace, why are there three separate mechanisms?

With AF_PACKET, I had previously attached to the existing `veth-af-host` interface and observed frames passing through it.

Conceptually:

```text
veth-af-host
    ↓
traffic on the interface
    ↓
AF_PACKET
    ↓
userspace observer
```

AF_PACKET did not create a new network interface here.

It gave me access to packets on an existing interface.

TAP is a different mechanism.

Creating a TAP device creates a new virtual Layer-2 network interface in Linux.

For example:

```text
tap0
```

Linux can treat this interface like other network interfaces.

The data TAP carries to userspace is at the Ethernet-frame level.

For this reason, the data structures visible through `AF_PACKET + SOCK_RAW` and TAP appear similar at first:

```text
AF_PACKET + SOCK_RAW
        ↓
[Ethernet][IP][UDP][Payload]


TAP
 ↓
[Ethernet][IP][UDP][Payload]
```

However, their operating models are not the same.

The fundamental difference:

```text
AF_PACKET
    ↓
accesses traffic on an existing network interface


TAP
    ↓
creates a virtual Layer-2 network interface attached to userspace
```

With AF_PACKET:

> "I want to see the frames passing through this interface."

whereas with:

TAP, the request is closer to:

> "I want to attach my userspace program to the packet path of a virtual Ethernet interface."


TUN also provides a virtual network interface, like TAP, but operates at Layer 3 rather than Layer 2.

TUN does not give userspace a frame beginning with an Ethernet header.

It provides a network-layer packet:

```text
TUN
 ↓
[IP][UDP][Payload]
```

This view resembles the `AF_PACKET + SOCK_DGRAM` result examined earlier:

```text
AF_PACKET + SOCK_DGRAM
        ↓
[IP][UDP][Payload]


TUN
 ↓
[IP][UDP][Payload]
```

Here too, however, the mechanisms are not the same.

`AF_PACKET + SOCK_DGRAM` accesses packet traffic on an existing interface through a packet socket, whereas:

TUN creates a virtual Layer-3 interface attached to a userspace program.

At this stage, I can keep the following distinction in mind:

```text
AF_PACKET
    ↓
attach to an existing interface


TAP
    ↓
virtual Layer-2 interface
    ↓
Ethernet frame


TUN
    ↓
virtual Layer-3 interface
    ↓
IP packet
```

In summary:

```text
AF_PACKET + SOCK_RAW
    ↓
[Ethernet][IP][UDP][Payload]

TAP
    ↓
[Ethernet][IP][UDP][Payload]


AF_PACKET + SOCK_DGRAM
    ↓
[IP][UDP][Payload]

TUN
    ↓
[IP][UDP][Payload]
```

The data view may be similar, but the attachment model is different.

AF_PACKET accesses traffic on an existing interface, while TAP and TUN act as virtual network interfaces between userspace and the Linux network stack.

### Creating a TAP Interface

I will begin learning by implementing it.

The difference between TUN and TAP was now experimentally clear:

```text

    ↓

    ↓

TUN
    ↓
[IP][...]
    ↓

```

Together with the earlier AF_PACKET experiments:

```text

    ↓

    ↓
```

```bash
cat /sys/class/net/veth-a-host/queues/rx-0/rps_cpus
```

Result:

```text
000
```

This value shows that the RPS CPU bitmap is empty for the relevant RX queue.

Therefore:

```text
veth-a-host
    ↓
rx-0
    ↓
rps_cpus = 000
    ↓
RPS disabled
```

was observed.

I also checked the number of CPUs visible to the container:

```bash
nproc
```

Result:

```text
11
```

The runtime environment therefore sees 11 logical CPUs.

However:

```text
available CPUs = 11
rps_cpus      = 000
```

so the presence of multiple CPUs does not mean that RPS is enabled automatically.

In other words:

```text
multiple CPUs available
        ≠
RPS enabled
```

### RFS

I then checked the receive flow-steering configuration:

```bash
cat /sys/class/net/veth-a-host/queues/rx-0/rps_flow_cnt
```

Result:

```text
0
```

This value shows that no RFS flow table is allocated for the relevant RX queue.

Conceptually:

```text
rx-0
    ↓
rps_flow_cnt = 0
    ↓
per-queue RFS flow table disabled
```

I then tried to check the global RFS flow-table configuration value:

```bash
cat /proc/sys/net/core/rps_sock_flow_entries
```

However:

```text
cat: /proc/sys/net/core/rps_sock_flow_entries: No such file or directory
```

I do not infer from this that the kernel definitely lacks support for the relevant feature.

The more cautious observation is:

```text
rps_cpus
    → present

rps_flow_cnt
    → present

rps_sock_flow_entries
    → not present in this runtime/container view
```


### Environment Limits and the RSS/RPS/RFS Distinction

I can summarize the fundamental distinction between RSS, RPS, and RFS as follows:

```text
RSS
    ↓
hardware / NIC side
    ↓
flow → RX queue distribution


RPS
    ↓
software / kernel side
    ↓
receive processing → CPU selection


RFS
    ↓
flow-aware extension of RPS
    ↓
aims to move flow processing closer to the CPU running the application
```

Results I observed directly in the current environment:

```text
CPU count:
11

veth-a-host:
rx-0
tx-0

veth-b-host:
rx-0
tx-0

rps_cpus:
000

rps_flow_cnt:
0

rps_sock_flow_entries:
not visible in the runtime/container
```

Within the scope of v1.9.8, I therefore draw the following conclusion:

```text
RSS:
- no physical multi-queue NIC
- hardware RSS was not directly verified
- only one RX queue was observed on the veth device

RPS:
- configuration surface was observed
- rps_cpus = 000
- disabled for the relevant RX queue

RFS:
- rps_flow_cnt = 0
- queue-level flow table disabled
- global rps_sock_flow_entries sysctl is not present in this runtime/container view
```

I was able to inspect the RSS/RPS configuration surfaces in this devcontainer environment, but I did not verify real hardware RSS scaling behavior. I also did not measure multi-core receive performance in this experiment. Observing a single RX queue does not, by itself, rule out distributing receive processing across CPUs with RPS; RPS was disabled for the queue examined here.

At this point, I consider the RSS/RPS exploration complete.

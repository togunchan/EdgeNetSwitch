# EdgeNetSwitch v2.0 — Runtime Maturity

## 1. Release Objective

v2.0 matures the existing networking runtime through deterministic lifecycle and shutdown contracts, bounded asynchronous telemetry, safe control-plane concurrency, lifecycle identity and accounting, and operational visibility and health. Regression coverage validates graceful degradation and continued progress after localized failures; the release does not introduce a new networking architecture.

## 2. Runtime Lifecycle and Shutdown

`PacketProcessor::stop()` explicitly closes queue admission, drains accepted packets, and joins the worker before returning. `TelemetryExportManager::stop()` closes sample admission, drains retained queued samples, and joins its export worker. Both destructors call `stop()` as a cleanup fallback, and sequential repeated stop is safe.

Both workers change shutdown state under the same queue mutex used by the condition-variable wait predicate, then notify after unlocking. This synchronizes admission and shutdown and prevents a lost notification between predicate evaluation and waiting. Workers exit only after stop is requested and their queues are empty.

Observer lifetime remains an ownership contract: `PacketStats` and other event consumers must remain alive while the packet worker publishes final events. Ingress and control producers must be quiescent before stopping and tearing down the processor. The daemon enforces this order:

```text
shutdown request
  -> publish Stopping / ShuttingDown snapshot
  -> close control admission
  -> stop epoll and join its thread
  -> destroy control socket; shut down ingress
  -> PacketProcessor::stop(): drain and join
  -> TelemetryExportManager::stop(): drain and join
  -> publish SystemShutdown
```

Explicit packet shutdown keeps observers alive through drain; destructor cleanup does not replace that ordering. See [daemon shutdown](../../src/daemon/main.cpp) and the [packet](../../tests/packet_runtime_lifecycle_tests.cpp) and [telemetry](../../tests/telemetry_lifecycle_tests.cpp) lifecycle regressions.

## 3. Telemetry Runtime Maturity

`TelemetryExportManager` uses a bounded queue and a background worker to export to multiple registered exporters. `start()` opens admission; enqueue before start or after stop is rejected.

At capacity, the queue evicts the oldest waiting sample and increments `dropped_count_`, exposed through `droppedCount()` and `telemetry_dropped_samples`. The sample already being exported is unaffected. Admission rejection is separate from capacity-drop accounting.

Each exporter call has its own exception boundary, covering standard and unknown exceptions. A failed exporter does not prevent remaining healthy exporters from receiving the sample or stop the worker from processing later samples. Shutdown drains samples retained after any drop-oldest eviction before joining. This is a drain contract, with no retry or guaranteed-delivery mechanism.

[Queue and exporter tests](../../tests/telemetry_export_manager_tests.cpp) verify capacity, eviction order, drop accounting, and exception isolation; [lifecycle tests](../../tests/telemetry_lifecycle_tests.cpp) verify asynchronous recovery and drain.

## 4. Safe Control-Plane Boundaries

| Boundary | v2.0 contract |
| --- | --- |
| `MacTable` | `learn()`, `lookup()`, `ageOut()`, `snapshot()`, and `size()` synchronize access with the same mutex. Snapshots are independent copies; formatting does not retain access to the live table. |
| Transport counters | Updates, reset, and copy-based snapshots synchronize through `counters_mutex_`. Backend I/O occurs outside this lock. |
| Control admission | `ControlServer::closeAdmission()` prevents new acceptance/dispatch past the admission checks. Work already past the final check may finish; the daemon joins the epoll thread before teardown. |
| Epoll lifecycle | A one-way `stop_requested_` preserves stop-before-run. Repeated stop is safe and only the first request signals the wakeup fd. The same loop object has no restart contract. |

These contracts are implemented in [MacTable](../../src/switching/MacTable.cpp), [TransportManager](../../src/transport/TransportManager.cpp), [ControlServer](../../src/control/ControlServer.cpp), and [EpollEventLoop](../../src/system/epoll/EpollEventLoop.cpp). [Control](../../tests/control_tests.cpp) and [epoll](../../tests/epoll_manager_tests.cpp) regressions cover admission closure and stop-before-run.

## 5. Lifecycle Identity and Accounting

One daemon-owned `LifecycleIdGenerator` supplies both UDP ingress and control-plane synthetic packets. `Packet::id` is packet/wire identity and may repeat, including fixed synthetic IDs; `lifecycle_id` identifies a runtime execution from the shared monotonic sequence.

`PacketStats` tracks active lifecycle IDs rather than subtracting aggregate ingress and terminal populations:

- `PacketRx` activates an ID unless it has already completed.
- The first `PacketProcessed` or `PacketDropped` completes that ID and removes it from the active set.
- A terminal-only drop before `PacketRx` does not cancel another active lifecycle.
- Repeated terminal events increment only `duplicate_events`, without changing terminal or outcome counts.
- If a synchronous subscriber publishes a terminal event before the stats subscriber sees `PacketRx`, that late ingress is counted without reactivating the completed ID.

`pending_terminal_events` is the active-set size. Ingress, processed, terminal, duplicate, pending, and drop fields are copied under one `lifecycle_mutex_` critical section. Other measurements have separate read paths; the snapshot is not a single transaction across every runtime metric. Published `RuntimeStatus` copies are immutable for control readers.

### Completed lifecycle retention

The previous completed-ID set retained one entry per terminal lifecycle indefinitely. Completed history now uses inclusive, disjoint lifecycle ranges, merging adjacent intervals and bridging gaps when missing completions arrive. Completing `6` between `[1,5]` and `[7,10]`, for example, produces `[1,10]` while preserving duplicate detection.

This avoids normal-runtime per-packet retention growth. The range representation is **not strictly bounded for arbitrary indefinitely sparse lifecycle IDs**. It is appropriate for EdgeNetSwitch's normal monotonic lifecycle generation and completion model.

[PacketStats](../../src/packet/PacketStats.cpp) and [packet pipeline regressions](../../tests/packet_pipeline_tests.cpp) establish active-ID accounting, terminal-before-ingress handling, duplicate detection, and range merging. [Control tests](../../tests/control_tests.cpp) verify repeated packet IDs with distinct lifecycle IDs.

## 6. Operational Visibility

### OV-1 — Packet Visibility

`packet-stats` and `packet-stats:json` expose distinct drop-reason keys, queue measurements, and forwarding counters. Drop serialization preserves `parse_error`, `validation_error`, `queue_overflow`, `rate_limited`, `datagram_truncated`, `simulated_loss`, `processing_error`, `internal_error`, and `unknown` independently.

| Measurement | Meaning |
| --- | --- |
| `queue_depth` | Waiting packets, excluding the packet in flight. |
| `queue_capacity` | Maximum waiting queue size. |
| `queue_high_water_mark` | Largest observed waiting depth; retained after drain. |
| `drops_by_reason[QueueOverflow]` | Packets rejected because the waiting queue was full. |
| `forwarding_drop_decisions` | `ForwardingAction::Drop` decisions. |
| `forwarding_flood_decisions` | `ForwardingAction::Flood` decisions. |
| `forwarding_forward_decisions` | `ForwardingAction::ForwardToPorts` decisions. |

`ForwardingAction::Drop != PacketDropped`: a forwarding Drop is a switching decision, not automatically a lifecycle failure. It may still be followed by `PacketProcessed`; forwarding counters remain separate from lifecycle drop accounting.

### OV-2 — Egress and Health Correctness

`TransportManager` is authoritative for egress-port attribution. Results for `Success`, `SendFailed`, `PortDown`, `InvalidPacket`, and `BackendUnavailable` retain the requested port, even if a backend returns a default or incorrect `port_id`.

Transport counters describe egress attempts: success increments `tx_packets` and `tx_bytes`; failures increment `tx_failed`, with additional category counters for unavailable backends, down ports, and invalid packets. These outcomes remain separate from packet lifecycle completion.

`HealthStatus::silence_duration_ms` reports elapsed time since the last heartbeat consistently in transition events and current status. The daemon calls `healthMonitor.onTick()` before `telemetry.onTick()`, evaluating existing silence before a synchronous telemetry heartbeat can refresh it. Regressions cover timeout transitions, silence reporting, heartbeat recovery, and transition-only event publication.

### OV-3 — Operational Health

| Model | Values |
| --- | --- |
| `RuntimeState` — lifecycle phase | `Booting`, `Running`, `Stopping` |
| `OperationalHealth` — operating condition | `Healthy`, `Degraded`, `Overloaded`, `ShuttingDown` |

`RuntimeStatusBuilder` derives operational health with this priority:

```text
ShuttingDown > Overloaded > Degraded > Healthy
```

`Stopping` always yields `ShuttingDown`. Otherwise, an increase in `QueueOverflow` since the previous snapshot build, or current saturation (`queue_capacity > 0` and `queue_depth >= queue_capacity`), yields `Overloaded`. Without overload, a timed-out heartbeat yields `Degraded`; otherwise health is `Healthy`.

Overload is non-sticky: it clears on a later snapshot when there is no new overflow and the queue is no longer saturated. A heartbeat timeout can still leave that snapshot `Degraded`. Lifetime overflow totals alone do not hold the runtime in `Overloaded`.

`status` and `status:json` expose `operational_health`. Shutdown publishes the `Stopping` / `ShuttingDown` snapshot before closing control admission.

Visibility and health contracts are covered by [control serialization tests](../../tests/control_tests.cpp), [snapshot tests](../../tests/snapshot_publisher_tests.cpp), [health status tests](../../tests/health_monitor_tests.cpp), and [health transition tests](../../tests/health_monitor_transition_tests.cpp).

## 7. Graceful Degradation and Recovery

### Packet queue pressure

A full packet queue rejects additional work with classified `QueueOverflow` drops while the runtime remains operational. Gated regressions fill the queue, verify overflow accounting, then release the worker and confirm all accepted packets drain, depth returns to zero, and the high-water mark remains visible.

### Failure injection

The current `FailureType` values and processor behavior are:

| FailureType | Result |
| --- | --- |
| `None` | Normal processing. |
| `MalformedPacket` | Terminal `PacketDropped` with `ParseError`. |
| `ValidationError` | Terminal `PacketDropped` with `ValidationError`. |
| `SimulatedLoss` | Terminal `PacketDropped` with `SimulatedLoss`. |
| `ArtificialDelay` | Configured delay in the synchronous publisher callback, followed by normal admission; no injected terminal drop. |
| `ProcessingRejection` | Terminal `PacketDropped` with `ProcessingError`. |

Sequential recovery regressions for malformed input, validation failure, and processing rejection observe the first drop, then verify that a later valid packet reaches `PacketProcessed` through the same `PacketProcessor` and unchanged injector. Final accounting is one drop, one processed packet, two terminals, zero duplicates, zero pending lifecycles, and an empty queue. `SimulatedLoss` already has mixed successful/dropped outcome coverage; delay coverage verifies continued processing without injected drops.

### Transport failure recovery

Separate regressions exercise `BackendUnavailable`, `PortDown`, `InvalidPacket`, and `SendFailed`. A transport failure does not automatically produce `PacketDropped`: under the current runtime model, that packet can still reach `PacketProcessed`.

After the failed attempt completes, a later packet successfully transmits through a healthy backend using the same processor runtime. The tests verify egress attribution, forwarding events, counters, packet identity, and payload. They prove continued processor progress, not restoration of the same failed backend.

### Telemetry exporter recovery

The asynchronous regression verifies that an exporter exception is isolated, a healthy exporter receives the first sample, and the worker processes later samples. Two samples queued after that exception drain during `stop()`. The throwing exporter is called three times, the healthy exporter receives `101, 102, 103` in order, no capacity drops occur, and the queue empties. Repeated stop is safe; post-stop sample `999` is rejected.

### Post-stop PacketProcessor admission

A newly published `PacketRx` after `PacketProcessor::stop()` completes must not execute `FailureInjector` or create new processor work. The early stopped-state guard runs before injection; the queue-locked check remains to preserve the enqueue/shutdown boundary. Regressions verify no new processor terminal/drop events or queued work after stop, including injected terminal-failure modes.

`PacketProcessor::stop()` is not a global completion barrier for arbitrary concurrent `MessagingBus` callbacks already past the admission guard. Other subscribers can also still observe a post-stop `PacketRx`. Runtime teardown therefore requires ingress/control producers to be quiescent before processor shutdown.

Recovery evidence is in [packet pipeline tests](../../tests/packet_pipeline_tests.cpp), [forwarding/transport runtime tests](../../tests/packet_forwarding_runtime_tests.cpp), [telemetry lifecycle tests](../../tests/telemetry_lifecycle_tests.cpp), and [post-stop packet tests](../../tests/packet_runtime_lifecycle_tests.cpp).

## 9. Known Boundaries

- `HealthMonitor` tests still depend on `system_clock` and timeout margins.
- A live control client reading the short `SHUTTING_DOWN` window is not covered by an end-to-end daemon shutdown integration test.
- Transport recovery tests use fake backend return statuses rather than real operating-system/backend failures.
- Lifecycle range compression assumes the normal monotonic generator/completion model; indefinitely sparse IDs can increase retained ranges.
- PacketProcessor teardown requires packet producers to be quiesced first; `stop()` is not a general barrier for already-running publisher callbacks.

These boundaries are not v2.0 blockers.
